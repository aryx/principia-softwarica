References for the "tools" books (research only; no .nw edited)
================================================================

Books covered: builders/Make.nw (+ builders/Intro.nw), shells/Shell.nw
(+ shells/Intro.nw), editors/ed.nw, utilities/Utilities.nw,
debuggers/Debugger.nw, debuggers/db.nw, debuggers/Debugger_x86.nw,
profilers/Profiler.nw, version_control/VCS.nw (+ Intro.nw, Overview.nw),
version_control/VCS_dulwich.nw.

Conventions:
- "chunk" entries go right before the <<chunk>>= line.
- "PROSE" entries (Intro/Overview principles sections) go right before
  the named paragraph (its %claude:/first line); subsection + first words
  are given.
- Existing bib keys are given as "bib: key"; entries without a key need
  a new bib entry (listed at the end).
- Line numbers are approximate (as of 2026-09-18).

Founding classic per field (the author's priority), and where it goes:
  build systems ... Feldman 1979 (Make)        -> builders/Intro.nw DFS
  shells .......... Pouzin 1965 (RUNCOM/SHELL) -> shells/Intro.nw
  line editors .... Deutsch & Lampson 1967 (QED) -> ed.nw
  regexps ......... Kleene 1956, Thompson 1968   -> Utilities grep, ed
  debugging ....... Gill 1951 (EDSAC)            -> Debugger.nw principles
  profiling ....... Knuth 1971 (FORTRAN study)   -> Profiler.nw principles
  version control . Rochkind 1975 (SCCS)         -> VCS Overview "Delta"
  diff ............ Hunt & McIlroy 1976          -> VCS Overview "diff"
  hashing-as-names  Merkle 1979/1987             -> VCS Overview objects

### builders/Intro.nw : PROSE, \subsubsection{Depth-first search}
(line ~1662, paragraph "Once the graph of dependencies is built, the main
algorithm behind [[mk]] is to perform a {\em depth-first search}"; the
author left "% cite cormen?" right there)
Algorithm/idea: DFS of the dependency DAG as the core of a build tool.
Verified: work() (Make.nw ~6849) is a recursive post-order DFS; Feldman's
  own abstract says "Make does a depth-first search of this graph".
CONFIDENCE: high
Proposed lines:
%ref: S. I. Feldman, "Make -- A Program for Maintaining Computer
%  Programs", Software: Practice and Experience 9(4):255-265, 1979
%  (bib: make) (the founding build-tool paper, written after a
%  colleague lost a morning debugging a program he had fixed but not
%  recompiled; its abstract already says "the description file
%  really defines the graph of dependencies; Make does a depth-first
%  search of this graph" -- exactly what [[work()]] does).
%ref: R. E. Tarjan, "Depth-first search and linear graph algorithms",
%  SIAM Journal on Computing 1(2):146-160, 1972 (the paper that made
%  DFS a general tool: classifies tree, back and cross edges; a back
%  edge is a cycle, which is what [[cyclechk()]] looks for).
%ref: T. H. Cormen, C. E. Leiserson, R. L. Rivest, C. Stein,
%  "Introduction to Algorithms", MIT Press, Section 22.3-22.4
%  (DFS with white/gray/black colors and topological sort: a build
%  order is a reverse post-order of the DAG).

### builders/Intro.nw : PROSE, \subsection{A job scheduler}
(line ~2055, paragraph "A build system maintains dependencies between
files efficiently firstly by being an {\em incremental} program.")
Algorithm/idea: a build system = scheduler + "is it up to date?" rebuilder.
Verified: outofdate() (Make.nw ~7039) is a pure mtime comparison; mk
  schedules in DFS order. build-alacarte is in the bib but cited nowhere.
CONFIDENCE: high
Proposed lines:
%ref: A. Mokhov, N. Mitchell, S. Peyton Jones, "Build Systems a la
%  Carte", ICFP 2018 (bib: build-alacarte) (splits every build system
%  into a scheduler and a rebuilder; in its taxonomy Make -- and so
%  [[mk]] -- is a topological scheduler with a modification-time
%  rebuilder, while Bazel or Shake use content hashes; useful to place
%  [[outofdate()]] on the map).

### Make.nw : <<function [[cyclechk]]>>
(line ~5787, section "Checking the graph and the rules" / "Cycle detection")
Algorithm/idea: cycle detection by DFS with an "on the recursion stack" mark.
Verified: sets CYCLE on entry, clears it on exit, reports if seen set:
  that is the "gray" state of the three-color DFS; the permanent "black"
  (done) state is NOT kept, so shared subgraphs are re-walked (cost is
  number of paths, not nodes) -- the author's own %-note wonders about it.
CONFIDENCE: high
Proposed lines:
%ref: R. E. Tarjan, "Depth-first search and linear graph algorithms",
%  SIAM Journal on Computing 1(2):146-160, 1972 (a cycle exists iff DFS
%  meets a back edge, i.e. a node still on the recursion stack -- the
%  [[CYCLE]] flag; Tarjan also keeps a "finished" mark so each node is
%  visited once, which [[cyclechk()]] omits, re-walking shared subgraphs).
%ref: A. B. Kahn, "Topological sorting of large networks", CACM
%  5(11):558-562, 1962 (road not taken: sorting by repeatedly removing
%  nodes with no remaining prerequisites finds cycles as a leftover, and
%  was written for PERT charts of 1960s engineering projects).

### Make.nw : <<function [[outofdate]]>>
(line ~7039, section "Exploring the graph: [[work()]]")
Algorithm/idea: the timestamp rule "target older than a prerequisite".
Verified: returns node->time <= arc->n->time (ties rebuild, as the C
  comment says); nonexistent files have time 0.
CONFIDENCE: high
Proposed lines:
%ref: S. I. Feldman, "Make -- A Program for Maintaining Computer
%  Programs", Software: Practice and Experience 9(4):255-265, 1979
%  (bib: make) (the rule itself: a target is rebuilt when it "has not
%  been modified since its generators were"; [[mk]] adds the choice of
%  treating equal times as out of date, safer on fast machines where
%  a compile finishes within the same second).

### Make.nw : <<function [[match]]>>
(line ~5407, section "Finding matching metarules" / "Matching a pattern")
Algorithm/idea: %-pattern metarules instead of Make's suffix rules.
Verified: match() finds the literal prefix, then the % stem, then checks
  the suffix; & variant excludes '/' and '.'.
CONFIDENCE: high
Proposed lines:
%ref: A. G. Hume, "Mk: a successor to make", USENIX Summer Conference,
%  1987 (bib: mk-successor) (introduces "pattern-matching metarules
%  rather than suffix transformation rules": Make could only say
%  ".c.o:", i.e. rewrite one suffix into another; [[mk]]'s [[%]]
%  matches anywhere in the name and binds [[$stem]], an idea GNU Make
%  later copied as its pattern rules).

### Make.nw : <<function [[ambiguous]]>>
(line ~6050, section "Ambiguous rules detection")
Algorithm/idea: rule priority (simple rule beats metarule) and ambiguity.
Verified: chunk "give priority to simple rules over meta rules"; errors
  when two recipes remain.
CONFIDENCE: high
Proposed lines:
%ref: A. G. Hume, "Mk: a successor to make", USENIX Summer Conference,
%  1987 (bib: mk-successor) (states the two rules implemented here:
%  "any non-metarule takes precedence over a metarule", and more than
%  one applicable recipe is an ambiguity error; Make instead silently
%  used the first matching suffix rule).

### Make.nw : <<global [[iflag]]>>
(line ~11717, section "Missing-intermediates optimization: [[mk -I]]")
Algorithm/idea: a missing intermediate need not be rebuilt if targets
  downstream are up to date w.r.t. the sources.
Verified: the PRETENDING machinery in work()/clrmade(); Hume's paper has
  a whole section "Missing intermediates" (with the -i flag at the time).
CONFIDENCE: medium (flag letter changed between paper and code: paper
  says -i suppresses it; check against this code's semantics before use)
Proposed lines:
%ref: A. G. Hume, "Mk: a successor to make", USENIX Summer Conference,
%  1987 (bib: mk-successor) (section "Missing intermediates": the
%  motivation was keeping only one copy of each object file, inside the
%  library archive, deleting the loose .o files without triggering a
%  rebuild of everything).

### Make.nw : <<function [[sched]]>>
(line ~7669, section "Scheduling Jobs" / "[[sched()]]")
Algorithm/idea: greedy list scheduling of ready jobs onto nproc slots.
Verified: pops the head of the FIFO [[jobs]] list into the next free
  slot (nextslot()); no priority, no critical-path estimate.
CONFIDENCE: high
Proposed lines:
%ref: R. L. Graham, "Bounds for certain multiprocessing anomalies",
%  Bell System Technical Journal 45(9):1563-1581, 1966 (list scheduling:
%  whenever a processor is free, start any ready task; Graham proved it
%  is never worse than twice optimal, and showed the "anomalies" where
%  more processors make things slower -- the policy [[sched()]] uses,
%  with the [[jobs]] list as the list).
%ref: T. C. Hu, "Parallel sequencing and assembly line problems",
%  Operations Research 9(6):841-848, 1961 (road not taken: start the
%  job on the longest remaining path first -- critical-path priority,
%  born on assembly lines; [[mk]] just takes jobs in DFS order).

### Make.nw : <<[[applyrules()]] if regexp rule then continue if some conditions>>
(line ~9827, section "Regular-expression rules: [[:R:]]")
Algorithm/idea: regular-expression metarules via libregexp (regexec +
  regsub with \1..\9 submatches).
Verified: calls regexec(r->pat, node->name, rmatch, NREGEXP) then
  regsub(); the matching engine itself lives in libregexp (Libcore).
CONFIDENCE: high
Proposed lines:
%ref: A. G. Hume, "Mk: a successor to make", USENIX Summer Conference,
%  1987 (bib: mk-successor) (section "More on metarules": the second
%  kind of metarule uses full egrep-style expressions, with the warning
%  that they are "significantly slower than % metarules" -- here each
%  candidate target costs a [[regexec()]] instead of a [[strcmp]]).
(Note: cite Thompson 1968 in the Libcore libregexp chapter, not here.)

### Make.nw : <<function [[symlook]]>>   (optional, low priority)
(line ~695, section "Symbol table" / "[[hash]]")
Algorithm/idea: chained hash table with a multiplicative string hash
  (h = h*79 + c, namespace folded into the seed), NHASH=4099 (prime).
Verified: chunk <<[[symlook()]] compute hash value>> and HASHMUL 79.
CONFIDENCE: high (but the same hash appears in many books: put the
  Knuth ref only in the book where the hash table is first introduced,
  probably Assembler/Linker)
Proposed lines:
%ref: D. E. Knuth, "The Art of Computer Programming, Vol. 3: Sorting
%  and Searching", Addison-Wesley, 1973, Section 6.4 (bib: taocp)
%  (hashing with chaining; why a prime table size like [[NHASH]]=4099
%  spreads multiplicative hash values better than a power of two).

## shells/Shell.nw
######################################################################

### Shell.nw : <<rc/syn.y>>
(line ~3586, section "Parsing" / "Overview")
Algorithm/idea: a real yacc (LALR) grammar for the shell, vs Bourne's
  hand-written parser.
Verified: rc/syn.y is a yacc grammar (yacc already cited in the Intro).
CONFIDENCE: high
Proposed lines:
%ref: T. Duff, "Rc -- The Plan 9 Shell", 1990 (bib: rc-plan9) (section
%  "Design Principles": "nobody really knows what the Bourne shell's
%  grammar is. Even examination of the source code is little help" --
%  the reason [[rc]] has a yacc grammar you can read in one page).
%ref: S. R. Bourne, "The UNIX Shell", Bell System Technical Journal
%  57(6):1971-1990, 1978 (the shell rc replaces; its parser was
%  hand-written recursive descent in C disguised as Algol 68 by macros,
%  and its input was re-scanned after substitution, the design choice
%  Duff's paper argues against).

### Shell.nw : <<priority and associativity declarations>>
(line ~3610, section "Parsing" / "Overview")
Algorithm/idea: resolving an ambiguous grammar with precedence and
  associativity declarations instead of rewriting it.
Verified: %left/%right lines for ^, |, &&, ||, etc. in syn.y.
CONFIDENCE: high
Proposed lines:
%ref: A. V. Aho, S. C. Johnson, J. D. Ullman, "Deterministic parsing
%  of ambiguous grammars", CACM 18(8):441-452, 1975 (the idea behind
%  yacc's [[%left]]/[[%right]]: keep the short ambiguous expression
%  grammar and let precedence rules settle each shift/reduce conflict,
%  instead of a longer grammar with one nonterminal per precedence
%  level).

### Shell.nw : <<[[main()]] interpreter loop>>
(line ~2221, section "Bytecode interpreter loop")
Algorithm/idea: threaded code: the program is an array of routine
  addresses, and the "interpreter" is a loop calling the next one.
Verified: runq->pc++; (*runq->code[runq->pc-1].f)(); Code cells hold a
  function pointer or an inline operand (struct Code ~1005). This is
  "call threading" (one indirect call per op), not Bell's jump-threading.
CONFIDENCE: high
Proposed lines:
%ref: J. R. Bell, "Threaded code", CACM 16(6):370-372, 1973 (written
%  for the PDP-11: compile a program to a list of routine addresses
%  and let each routine jump to the next; [[rc]]'s [[Code]] array is
%  that list, but [[rc]] returns to this [[for]] loop after each
%  routine instead of jumping directly, trading a little speed for
%  portable C; same model as Forth).

### Shell.nw : <<function [[execforkexec]]>>
(line ~5182, section "Simple commands" / "[[exec()]]")
Algorithm/idea: process creation split into fork + exec.
Verified: forks, and the child execs the command (search in $path).
CONFIDENCE: high
Proposed lines:
%ref: D. M. Ritchie, K. Thompson, "The UNIX Time-Sharing System",
%  CACM 17(7):365-375, 1974 (the fork/exec split and the shell
%  described as an ordinary program: between [[fork]] and [[exec]] the
%  child can rearrange its own file descriptors, which is how all
%  redirections and pipes of this chapter are implemented).

### Shell.nw : <<function [[Xbackq]]>>
(line ~10260, section "Command substitution")
Algorithm/idea: `{cmd} as a unary operator whose operand is already
  parsed, and output split into a list, never re-scanned.
Verified: Xbackq forks the pre-compiled code, reads the pipe, splits on
  $ifs into words.
CONFIDENCE: high
Proposed lines:
%ref: T. Duff, "Rc -- The Plan 9 Shell", 1990 (bib: rc-plan9) (section
%  "Design Principles": rc "is not a macro processor"; in Bourne's
%  `...` the command is a string re-parsed later, so nesting needs
%  backslashes exponential in the depth; with `{...} it is parsed
%  once, with the enclosing command, and [[Xbackq()]] only runs it).

### Shell.nw : <<function [[Xifnot]]>>
(line ~6643, section "Control flow statements" / "[[if]]")
Algorithm/idea: "if not" as a separate statement testing a flag left
  by the previous if.
Verified: global ifnot set by Xif/Xwastrue, checked by Xifnot; outcode
  sanity-checks that the last command was an if.
CONFIDENCE: high
Proposed lines:
%ref: T. Duff, "Rc -- The Plan 9 Shell", 1990 (bib: rc-plan9) (Duff
%  calls this his "admittedly feeble solution": an interactive shell
%  must run [[if(...) cmd]] as soon as the newline is typed, so it
%  cannot wait to see whether an [[else]] follows; hence a separate
%  statement and the [[ifnot]] flag).

### Shell.nw : <<function [[Xpipefd]]>>
(line ~10440, section "Process substitution")
Algorithm/idea: <{cmd} names a pipe end as a file (/fd/N).
Verified: pipe()+fork(); passes "/fd/%d" (Fdprefix) as the argument.
CONFIDENCE: high
Proposed lines:
%ref: T. Duff, "Rc -- The Plan 9 Shell", 1990 (bib: rc-plan9) (section
%  "Pipeline branching", e.g. [[cmp <{old} <{new}]]; it works only
%  because Plan 9 names every open file descriptor in [[/fd/]], so a
%  pipe end can be passed to any program as an ordinary file name).

### Shell.nw : <<function [[match]]>>
(line ~9314, section "Matching one name: [[match()]]")
Algorithm/idea: glob matching; * handled by recursive backtracking.
Verified: the prose says "[[*]] tries every possible suffix via recursion
  (backtracking)": exponential on patterns like a*a*a*b.
CONFIDENCE: high (web article, not a paper)
Proposed lines:
%ref: R. Cox, "Glob Matching Can Be Simple And Fast Too",
%  research.swtch.com/glob, 2017 (road not taken: recursion on each
%  [[*]] is exponential for patterns like [[a*a*a*b]]; since a later
%  [[*]] can absorb whatever an earlier one would, remembering only the
%  last [[*]] position makes matching linear -- rc, like many shells
%  of its time, backtracks).

### Shell.nw : <<function [[heredoc]]>>   (medium value)
(line ~10859, section "Here documents")
Algorithm/idea: here documents copied into a temp file then opened as
  stdin, with $var substitution.
Verified: heredoc() writes the collected lines to a /tmp file (psubst
  substitutes variables).
CONFIDENCE: medium (that here documents originate in the Bourne shell)
Proposed lines:
%ref: S. R. Bourne, "An Introduction to the UNIX Shell", Unix
%  Programmer's Manual Vol 2a, 1979 (bib: sh) (here documents, [[<<]],
%  come from the Bourne shell; the text between the two markers is
%  saved to a temporary file, then opened as standard input -- same
%  implementation here).

### Shell.nw : <<function [[nextutf]]>>   (skip if Libcore already has it)
(line ~10168, section "Unicode")
Algorithm/idea: UTF-8 decoding by leading-byte length.
Verified: nextutf/equtf step by UTF-8 sequence length.
CONFIDENCE: high
Proposed lines:
%ref: R. Pike, K. Thompson, "Hello World or Kalimera kosme or Konnichiwa
%  Sekai", USENIX Winter Conference, 1993 (the UTF-8 paper: an encoding
%  designed on a diner placemat so that ASCII bytes never appear inside
%  a multi-byte character; that property is why [[rc]]'s lexer can keep
%  scanning for [[|]] or [[;]] byte by byte and only [[nextutf()]] needs
%  to know about sequence lengths).

### ed.nw : PROSE, \subsection{A line editor}
(line ~85, paragraph "[[ed]], short for ``editor'' ... is one of the
oldest \unix programs, originally written by Ken Thompson in the 1970s.")
Algorithm/idea: QED, the ancestor of ed (line addressing, /re/, s///).
Verified: ed's command/address language is the QED subset Thompson kept.
CONFIDENCE: high
Proposed lines:
%ref: L. P. Deutsch, B. W. Lampson, "An online editor", CACM
%  10(12):793-799, 1967 (QED, written for the SDS 940 time-sharing
%  system at Berkeley and used from teletypes, hence one line at a
%  time; Thompson reimplemented QED for CTSS and Multics before
%  distilling it into [[ed]]).
%ref: D. M. Ritchie, "An incomplete history of the QED text editor",
%  web page, Bell Labs (the chain QED -> Thompson's QED -> [[ed]] ->
%  [[sam]], by someone who used them all).

### ed.nw : <<function [[compile]](ed.c)>>
(line ~3045, section "Reading and compiling a regexp: [[compile()]]")
Algorithm/idea: compile a regexp once, then match every line with it.
Verified: collects the pattern, calls regcomp() from libregexp; match()
  calls rregexec(). Differs from Thompson: no machine code; libregexp
  builds an NFA program run by a VM tracking submatches (Pike's
  extension, from sam).
CONFIDENCE: high
Proposed lines:
%ref: K. Thompson, "Regular expression search algorithm", CACM
%  11(6):419-422, 1968 (written for QED on the IBM 7094: compiles the
%  expression into 7094 machine code that simulates all NFA states in
%  parallel, so matching is linear in the line length; [[regcomp()]]
%  still compiles once per pattern, but to a program for a small
%  interpreter instead of machine code).
%ref: R. Cox, "Regular Expression Matching: the Virtual Machine
%  Approach", research.swtch.com/regexp2, 2009 (explains the Thompson
%  VM with submatch tracking that Rob Pike wrote for [[sam]] and that
%  became [[libregexp]]; the [[subexp]] array here is its output).

### ed.nw : <<function [[reverse]](ed.c)>>
(line ~2587, section "[[m]]oving and copying lines")
Algorithm/idea: block move by three reversals.
Verified: move() calls reverse() three times on the line-pointer array
  (prose already cites programming-pearls; the author's % note says the
  trick is due to Gries and Mills).
CONFIDENCE: medium (report number)
Proposed lines:
%ref: D. Gries, H. D. Mills, "Swapping sections", Technical Report
%  TR 81-452, Cornell University, 1981 (the original analysis of
%  swapping two adjacent blocks in place; the three-reversal version
%  that [[move()]] uses is one of their algorithms -- note that [[ed]]
%  only reverses an array of line offsets, never the text itself).

### ed.nw : <<globals ed.c>> declaring [[zero]]   (medium value)
(line ~495, section "The lines as file offsets: [[zero]]")
Algorithm/idea: text in a scratch file, memory holds only one offset
  per line.
Verified: zero[] is an int array of offsets into tfile.
CONFIDENCE: medium (chapter title from memory)
Proposed lines:
%ref: B. W. Kernighan, P. J. Plauger, "Software Tools", Addison-Wesley,
%  1976 (bib: software-tools), chapter "Editing" (rebuilds a small
%  [[ed]] with the same design: text in a scratch file, an array of
%  line pointers in memory -- a design forced by the PDP-11's 64K
%  address space, and kept because moving lines means moving integers).
