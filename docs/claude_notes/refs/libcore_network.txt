Academic references for the core-library and network books
===========================================================
Books: lib_core/Libcore.nw, lib_core/Libcore_big.nw,
lib_networking/Network.nw, lib_networking/Network_v6.nw,
networking/Network_apps.nw

Research only; no .nw or source files were edited. Each entry was checked
against the chunk body in the .nw file (and against the synced C file when
the helper lives in an _extra.nw appendix). The parentheticals follow the
BRIEF addendum: they say what problem or machine the paper was written for,
which idea maps to which function here, and where Plan 9 differs.

Two of the Plan 9 papers are in the repo, and the venues below come from
their own footnotes:
  docs/articles/utf.ms      -> Pike & Thompson, Winter 1993 USENIX, pp. 43-50
  networking/docs/net/net.ms -> Presotto & Winterbottom, Winter 1993 USENIX,
                               pp. 271-280
  networking/docs/il/il.ms   -> Presotto & Winterbottom, "The IL Protocol"
                               (Plan 9 Programmer's Manual, 2nd ed., 1995)
  docs/articles/lexnames.ms  -> Pike, "Lexical File Names in Plan 9"
                               (the file has no venue footnote; see the
                               entry for how sure I am of the venue)

Problems I found in the existing prose while checking the code (not
refs, but the author should know about them):
  * Libcore.nw, qsort prose (~line 1831) says qsorts "recurses on the
    smaller partition and loops on the larger, which limits stack depth
    to O(log n)". The code does the OPPOSITE: `if(j >= n) { qsorts(a, j,
    p); ...}` recurses on the LEFT part when it is the LARGER one, and
    loops on the smaller one. So the worst-case stack depth is O(n).
  * Libcore.nw, pool prose (~lines 4027, 4154) calls the free tree
    "balanced". treeinsert/treedelete in libc/port/pool.c
    (Libcore_extra.nw) do no rebalancing at all. It is a plain,
    unbalanced binary search tree keyed on size.
  * Network.nw, balancetree prose (~line 8533) says "AVL-style
    rotations". The code does only single rotations and has no
    double-rotation case, so it is weaker than AVL. The ref entry below
    says so.

### Libcore.nw : <<function [[qsorts]]>>
(line ~1934, section "Complex types", subsection "Arrays (and [[qsort()]])")
Algorithm/idea: quicksort (partition-exchange sort)
Verified: swaps the pivot to a[0], runs Hoare-style pi/pj scans inward and
          swaps, puts the pivot in place at pj, then recurses on one side
          and loops on the other. It recurses on the LARGER side (see the
          prose problem above), unlike Sedgewick's advice.
CONFIDENCE: high
Proposed lines:
%ref: C. A. R. Hoare, "Algorithm 64: Quicksort", Communications of the
%  ACM 4(7):321, 1961; and "Quicksort", The Computer Journal 5(1):10-16,
%  1962 (Hoare came up with it in Moscow, where he needed to sort the
%  words of a sentence before looking them up in a Russian-English
%  dictionary on tape. The two pointers scanning toward each other are
%  his, and they are exactly [[pi]] and [[pj]] here).
%ref: R. Sedgewick, "Implementing Quicksort programs", Communications of
%  the ACM 21(10):847-857, 1978 (recurse on the SMALLER subfile and loop
%  on the larger to keep the stack at O(log n). [[qsorts]] does the
%  reverse: it recurses on the larger side when [[j >= n]]).

### Libcore.nw : <<function [[pivot]]>>
(line ~1905, same subsection)
Algorithm/idea: median-of-three pivot selection
Verified: samples the elements at n/6, n/2 and 5n/6 and returns the median,
          but only when n > 10 (below that, qsorts takes the middle
          element). There is no insertion-sort cutoff for small n.
CONFIDENCE: high
Proposed lines:
%ref: R. C. Singleton, "Algorithm 347: An efficient algorithm for sorting
%  with minimal storage", Communications of the ACM 12(3):185-187, 1969
%  (median of the first, middle and last elements, which protects
%  against already-sorted input. [[pivot]] samples at 1/6, 1/2 and 5/6
%  instead).
%ref: J. L. Bentley and M. D. McIlroy, "Engineering a sort function",
%  Software--Practice and Experience 23(11):1249-1265, 1993 (road not
%  taken: this rewrite of the Unix qsort adds a "ninther" pivot for large
%  arrays, an insertion-sort cutoff and a fat three-way partition for
%  equal keys. Plan 9's qsort has none of these).

### Libcore.nw : <<struct [[Btail]]>>
(line ~4131, section "Data structures" of chapter Memory Management)
Algorithm/idea: boundary tags (the block size stored at both ends)
Verified: Btail repeats Bhdr's size at the end of each block. B2PT/T2HDR
          step back from a header to the left neighbor's header in O(1),
          which is what blockmerge needs to coalesce on free.
CONFIDENCE: high
Proposed lines:
%ref: D. E. Knuth, The Art of Computer Programming, Vol. 1: Fundamental
%  Algorithms, Addison-Wesley, 1968, Section 2.5 "Dynamic Storage
%  Allocation" (Algorithm C, "liberation with boundary tags": putting
%  the size and a free bit at BOTH ends of a block lets [[free]] find the
%  left neighbor without a search. That is [[Btail]] plus [[B2PT]]).
%ref: K. C. Knowlton, "A fast storage allocator", Communications of the
%  ACM 8(10):623-625, 1965 (road not taken: the buddy system, which
%  rounds sizes up to powers of two so that a block's neighbor, its
%  "buddy", can be found from its address alone, with no tags).

### Libcore.nw : <<struct [[Free]]>>
(line ~4189, same section)
Algorithm/idea: best fit through a binary search tree keyed on size
Verified: left/right form a BST on size, and next/prev chain the blocks of
          equal size. treelookupgt returns the smallest size >= the
          request (best fit). treedelete replaces a node that has two
          children by its in-order successor. The tree is NOT balanced
          (see above).
CONFIDENCE: high
Proposed lines:
%ref: T. N. Hibbard, "Some combinatorial properties of certain trees with
%  applications to searching and sorting", Journal of the ACM 9(1):13-28,
%  1962 (the first analysis of the binary search tree, and the origin of
%  deleting a two-child node by moving its in-order successor up, as
%  [[treedelete]] does. Like Hibbard's trees, [[Pool]]'s free tree is
%  never rebalanced).

Algorithm/idea: format-directed output (a format string of literal text

Verified: dofmt copies literal text until '%', then looks the verb up in
          the fmtinstall-able table (_fmtdispatch). The user-installable

CONFIDENCE: high for the paper. The ancestry claim (FORMAT -> printf) is

Proposed lines:
%ref: J. W. Backus et al., "The FORTRAN automatic coding system", Proc.

%  FORTRAN's list of directives was fixed. [[fmtinstall]] lets a program
%  add its own verbs).

### Libcore.nw : <<function [[chartorune]]>>
(line ~5693, section "Runes")
Algorithm/idea: UTF-8 decoding
Verified: the T(i)/RuneX(i) macros give the prefix byte for an i-byte
          sequence and the largest rune it can hold. The loop checks the
          continuation bytes (10xxxxxx). The length test rejects
          overlong forms (the prose writes the test as "l <= RuneX(i)"), and
          there is a check that rejects surrogates.
CONFIDENCE: high (the venue and pages are from the utf.ms footnote)
Proposed lines:
%ref: R. Pike and K. Thompson, "Hello World or Kalimera kosme or
%  Konnichi wa Sekai", Proc. Winter 1993 USENIX Conference, pp. 43-50,
%  1993 (in repo: docs/articles/utf.ms. The encoding was designed on a
%  diner placemat in September 1992 to replace X/Open's FSS-UTF. The
%  leading byte gives the sequence length, which is [[T]] here, and
%  bytes below 0x80 are always ASCII, so [[strchr]] and friends still
%  work).
%ref: F. Yergeau, "UTF-8, a transformation format of ISO 10646", RFC
%  3629, 2003 (where the rules this code enforces became normative:
%  overlong forms are illegal and surrogates are excluded).

Verified: strchr finds each occurrence of the first character, then the
          code compares the rest byte by byte. The worst case is O(nm).
CONFIDENCE: high
Proposed lines:
%ref: D. E. Knuth, J. H. Morris and V. R. Pratt, "Fast pattern matching

Verified: regcomp1 turns the pattern into an array of Reinst (RUNE, OR,
          LBRA/RBRA, CCLASS, END...). This is Thompson's construction,
          with bytecode where Thompson emitted IBM 7094 machine code.
CONFIDENCE: high
Proposed lines:
%ref: S. C. Kleene, "Representation of events in nerve nets and finite

%  Princeton University Press, 1956 (regular expressions were invented to

%  operators union, concatenation and star are the [[OR]], implicit CAT
%  and [[STAR]] tokens parsed here).

### Libcore.nw : <<function [[regcomp1]]>>  (second, optional entry)

Algorithm/idea: operator-precedence parsing with an operand stack and an

Verified: regcomp.c's operator()/operand()/evaluntil() (the chunks are

CONFIDENCE: medium (I am sure of the idea and the 1961 Mathematisch

### Libcore.nw : <<function [[regexec1]]>>
(line ~7334, section "Execution: [[regexec()]]")
Algorithm/idea: Thompson NFA simulation, as a Pike VM with submatch
                tracking
Verified: two Relist arrays (current and next) of threads (pc plus a
          Resub). Every thread advances once per input character, and
          _renewthread drops duplicate pcs, so the time is O(nm) with no
          backtracking.
CONFIDENCE: high
Proposed lines:
%ref: K. Thompson, "Regular expression search algorithm", Communications
%  of the ACM 11(6):419-422, 1968 (written for the QED editor on CTSS:
%  follow every NFA state at once, one input character at a time, never
%  backtracking. The current and next lists here are his CLIST/NLIST,
%  and each list entry also carries a [[Resub]] for submatches).
%ref: R. Cox, "Regular Expression Matching: the Virtual Machine
%  Approach", swtch.com/~rsc/regexp/regexp2.html, 2009 (a modern
%  retelling that names this design the "Pike VM" and credits it to
%  Rob Pike's sam and this libregexp).

### Libcore.nw : <<function [[NaN]]>>
(line ~8393, section "Floats", subsection "Special numbers")
Algorithm/idea: IEEE 754 special values (NaN, infinities)
Verified: NaN sets the exponent to all ones (2047<<20 in the high word)
          and makes the mantissa non-zero. Inf does the same with a zero
          mantissa.
CONFIDENCE: high
Proposed lines:
%ref: IEEE Standard for Binary Floating-Point Arithmetic, ANSI/IEEE Std

%  infinities and NaNs. William Kahan designed the standard around what

%  floating-point arithmetic", ACM Computing Surveys 23(1):5-48, 1991

### Libcore.nw : <<function [[strtod]]>>
(line ~8520, section "Floats", subsection "Parsing")
Algorithm/idea: correctly rounded decimal-to-binary conversion
Verified: the decimal digits are normalized to .5xxx by divascii/mulascii,
          then the code binary-searches the Prec-word mantissa, comparing
          each candidate exactly with fpcmp, and rounds half-to-even at
          Sigbit. It uses no fast path and no floating-point estimate.
CONFIDENCE: high
Proposed lines:
%ref: W. D. Clinger, "How to read floating point numbers accurately",
%  Proc. ACM PLDI '90, SIGPLAN Notices 25(6):92-101, 1990 (the first
%  proof that input can always be rounded correctly, using bignums only
%  when floating point cannot decide. [[strtod]] always uses
%  multi-precision: it binary-searches the mantissa ([[low]], [[mid]],
%  [[hig]]) and compares each guess exactly, which is simpler and slower
%  than Clinger).
%ref: G. L. Steele Jr. and J. L. White, "How to print floating-point
%  numbers accurately", same proceedings, pp. 112-126, 1990 (the reverse
%  direction, done by [[fltfmt.c]], which this book does not show).

### Libcore.nw : <<function [[pow]]>>
(line ~9220, section "Floats", subsection "[[pow()]]")
Algorithm/idea: right-to-left binary exponentiation (repeated squaring)
Verified: `if(i & 1) xy *= x; i >>= 1; x *= x;`. The twist is that it
          works on the frexp mantissa and adds the exponents (ex/ey)
          separately, so the intermediate values never overflow.
CONFIDENCE: high
Proposed lines:
%ref: D. E. Knuth, The Art of Computer Programming, Vol. 2: Seminumerical
%  Algorithms, Addison-Wesley, 1969, Section 4.6.3 "Evaluation of Powers"
%  (Algorithm A, the right-to-left binary method. Knuth traces the idea
%  back to Pingala's Sanskrit work on prosody, around 200 B.C.
%  [[pow]] runs it on [[frexp]] mantissas and tracks the exponents in
%  [[ex]] and [[ey]] separately, so it never overflows early).

### Libcore.nw : <<function [[lrand]]>>

Algorithm/idea: additive (lagged-Fibonacci) generator
Verified: x = (*rng_feed + *rng_tap) & MASK over a 607-entry ring, with

CONFIDENCE: high
Proposed lines:
%ref: D. E. Knuth, The Art of Computer Programming, Vol. 2: Seminumerical

%  generator X[n] = X[n-24] + X[n-55] mod m, due to G. J. Mitchell and

### Libcore.nw : <<function [[isrand]]>>
(line ~10190, same section)
Algorithm/idea: Lehmer multiplicative congruential generator (the
                "minimal standard"), computed without overflow by
                Schrage's method
Verified: x = A*lo - R*hi with A = 48271, M = 2^31-1, Q = M/A = 44488 and
          R = M%A = 3399, and a correction when the result is negative.
          It is used only to seed the 607-entry ring.
CONFIDENCE: high for Lehmer and Park-Miller; medium for the exact Schrage
          venue
Proposed lines:
%ref: D. H. Lehmer, "Mathematical methods in large-scale computing
%  units", Proc. 2nd Symposium on Large-Scale Digital Calculating
%  Machinery (Harvard, 1949), 1951 (the first congruential generator,
%  x[n+1] = a x[n] mod m, first run on ENIAC. [[isrand]] is that
%  recurrence).
%ref: S. K. Park and K. W. Miller, "Random number generators: good ones
%  are hard to find", Communications of the ACM 31(10):1192-1201, 1988
%  (the "minimal standard" with m = 2^31-1. Its multiplier 16807 was
%  later replaced by 48271, the [[A]] here. The [[Q]]/[[R]] split that
%  avoids 32-bit overflow is Schrage's trick, explained in this paper).

### Libcore.nw : <<function [[hufftab]]>>
(line ~10919, section "Inflation (decompression)", subsection "Huffman
tree decoding")
Algorithm/idea: canonical Huffman codes, decoded from code lengths only
Verified: hufftab rebuilds the codes from bitcount[] alone (mincode =
          code<<1 for each length) and stores maxcode[]/last[] per
          length, plus a flat lookup table of flatbits bits. Its own
          comment says it relies on the fact that "shorter codes are
          assigned smaller lexical prefixes", which is the canonical
          property.
CONFIDENCE: medium (I am confident the paper exists and is the origin of
          canonical codes; volume and pages are from memory)
Proposed lines:
%ref: E. S. Schwartz and B. Kallick, "Generating a canonical prefix
%  encoding", Communications of the ACM 7(3):166-169, 1964 (if codes of
%  each length are handed out in numerical order, the code lengths alone
%  determine the whole code. That is why a DEFLATE block sends only
%  lengths, and why [[hufftab]] can rebuild the codes with the
%  [[mincode]] recurrence).

### Libcore.nw : <<function [[lzcomp]]>>
(line ~11276, section "Deflation (compression)", subsection "LZ77
matching")
Algorithm/idea: LZ77 sliding-window matching with hash chains
Verified: hashit hashes the next 3 bytes (MinMatch). hash[]/nexts[]
          chain the earlier positions with the same hash. lzmatch walks
          the chain up to maxcheck. Matches shorter than MinMatch are
          sent as literals (the LZSS rule), and matching is lazy
          (prevlen/prevoff). hashit (in Libcore_extra.nw) is
          multiplicative: ((c & 0xffffff) * 0x6b43a9b5) >> (32-HashLog).
CONFIDENCE: high
Proposed lines:
%ref: J. Ziv and A. Lempel, "A universal algorithm for sequential data
%  compression", IEEE Transactions on Information Theory IT-23(3):337-343,
%  1977 (LZ77: replace a repeated string by a (distance, length) pointer
%  back into a sliding window of the recent input. Here the window is
%  [[lz->hist]] and the pointers are the [[m]]/[[runlen]] results of
%  [[lzmatch]]).
%ref: J. A. Storer and T. G. Szymanski, "Data compression via textual
%  substitution", Journal of the ACM 29(4):928-951, 1982 (LZSS: send a
%  literal whenever a pointer would cost more, which is DEFLATE's
%  [[MinMatch]] of 3. Finding matches by chaining hash buckets
%  ([[hash]], [[nexts]]) and the multiplicative [[hashit]] are the
%  hashing of Knuth Vol. 3, Section 6.4).

### Libcore.nw : <<function [[adler32]]>>
(line ~12133, section "Checksums")
Algorithm/idea: Fletcher-style checksum (two running sums)
Verified: s1 += byte, s2 += s1, both mod 65521 (ADLERBASE, the largest
          prime below 2^16). The loop is unrolled by 16, and the modulo is
          done only every ADLERITERS (5552) bytes.
CONFIDENCE: high
Proposed lines:
%ref: J. G. Fletcher, "An arithmetic checksum for serial transmissions",
%  IEEE Transactions on Communications COM-30(1):247-252, 1982 (written at
%  Lawrence Livermore for serial links: a sum of bytes plus a sum of those
%  sums, so that swapped bytes are detected, which a plain sum misses.
%  That is [[s1]]/[[s2]]. Mark Adler's variant, specified in RFC 1950
%  (1996), uses the prime 65521 as modulus instead of 255 or 65535).

### Libcore.nw : <<function [[blockcrc]]>>
(line ~12207, same section)
Algorithm/idea: CRC-32, computed a byte at a time with a table
Verified: crc = crctab[(crc ^ byte) & 0xff] ^ (crc >> 8), the reflected
          form. mkcrctab (Libcore_extra.nw) builds the 256 entries by
          shifting 8 times with the polynomial passed in (0xEDB88320 for
          gzip).
CONFIDENCE: high
Proposed lines:
%ref: W. W. Peterson and D. T. Brown, "Cyclic codes for error detection",
%  Proceedings of the IRE 49(1):228-235, 1961 (treat the message as a
%  polynomial over GF(2) and send the remainder of its division by a
%  generator. The paper showed how to do this in hardware with a shift
%  register, which is the inner loop of [[mkcrctab]]).
%ref: D. V. Sarwate, "Computation of cyclic redundancy checks via table
%  look-up", Communications of the ACM 31(8):1008-1013, 1988 (precompute
%  8 shift-register steps into a 256-entry table so that software handles
%  a whole byte at once: the single line of [[blockcrc]]).

### Libcore.nw : <<function [[encrypt]]>>
(line ~15428, section "Cryptography")
Algorithm/idea: DES block cipher (Feistel network)
Verified: key_setup plus block_cipher on 8-byte DES blocks. The buffer
          pointer advances by 7, so consecutive blocks overlap by one
          byte, and a final partial block is handled by overlapping it
          with the previous one. That is not one of the standard FIPS 81
          modes (ECB/CBC/...).
CONFIDENCE: high
Proposed lines:
%ref: National Bureau of Standards, "Data Encryption Standard", FIPS PUB
%  46, 1977 (DES: 16 rounds of a Feistel network on 64-bit blocks with a
%  56-bit key. [[encrypt]] walks the buffer 7 bytes at a time, so its
%  8-byte DES blocks overlap. This is a Plan 9 chaining scheme, not one
%  of the standard modes).
%ref: H. Feistel, "Cryptography and computer privacy", Scientific
%  American 228(5):15-23, 1973 (the IBM Lucifer design, from which DES
%  came, and the Feistel round structure inside [[block_cipher]]).

### Libcore.nw : <<function [[lock]]>>
(line ~15840, section "Locks")
Algorithm/idea: mutual exclusion from a counting semaphore plus an atomic

- Network NE2000/dp8390 (ring buffer, multicast hash filter): hardware
