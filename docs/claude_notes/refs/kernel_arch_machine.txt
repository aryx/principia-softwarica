References research: Kernel_x86.nw, Kernel_arm.nw, Machine.nw
=============================================================

Scope notes
-----------
- kernel/Kernel_x86.nw is the old "x86 (32 bits) edition" material that
  used to be in the main text of Kernel.nw. It is still in SRC_ORIG
  (synced) but its #include in Kernel.nw is commented out
  (Kernel.nw:48982), so its %ref: lines would not render in the PDF
  today. The entries below are still tied to real x86 code
  (kernel/*/386/).
- kernel/Kernel_arm.nw is an appendix (#include'd at Kernel.nw:48826)
  that mostly holds FILE SKELETONS; the bodies of the interesting ARM
  functions (mmuinit, arch_tas, cas32, trap, clock...) live in
  Kernel.nw, which is outside this assignment. Only the peripheral
  drivers (DMA, GPIO, mini UART, eMMC, USB, ATAGs, coprocessor access)
  have their bodies here, so the ARM entries are mostly datasheet/spec
  references tied to those chunks.
- machine/Machine.nw is the book on 5i, the Plan 9 user-mode ARM
  emulator (interpreter + built-in adb-like debugger + profiler).
  It has the richest set of classic-paper hooks.
- Existing bib keys used/mentioned: x86-refman (Intel 80386 PRM, 1986),
  arm-refman (Seal, ARM ARM, 2001), lions, taocp, blit.

### Kernel_x86.nw : <<function [[tas]](x86)>>
(line ~609, section "[[arch_tas()]] (x86)")
Algorithm/idea: test-and-set via an atomic exchange (XCHG), the
  hardware primitive under the spin lock.
Verified: MOVL $0xDEADDEAD,AX; XCHGL AX,(BX) -- returns old key; lock()
  in concurrency/taslock.c spins on it (tas()==0 means acquired).
  XCHG with memory is implicitly LOCKed on x86.
CONFIDENCE: high
Proposed lines:
%ref: E. W. Dijkstra, "Solution of a problem in concurrent programming
%  control", CACM 8(9):569, 1965 (N processes sharing one memory with
%  no atomic read-modify-write, so mutual exclusion takes a clever
%  protocol of plain loads and stores; the 386's XCHG does the whole
%  job in one bus-locked instruction, which is all arch_tas needs).

### Kernel_x86.nw : <<function [[mb386]](x86)>>
(line ~666, section "[[arch_coherence()]] (x86)")
Algorithm/idea: memory barriers / memory consistency models.
Verified: three variants chosen at archinit time: mb386 (IRET is
  serializing), mb586 (CPUID is serializing), mfence (SSE2 MFENCE,
  emitted as raw bytes 0f ae f0). arch_coherence points to one of them.
CONFIDENCE: high
Proposed lines:
%ref: L. Lamport, "How to make a multiprocessor computer that correctly
%  executes multiprocess programs", IEEE Trans. Computers
%  C-28(9):690-691, 1979 (a two-page paper defining "sequential
%  consistency": what programmers assume and what caches and write
%  buffers silently break; arch_coherence is how the kernel puts it
%  back where it matters).
%ref: P. Sewell, S. Sarkar, S. Owens, F. Zappa Nardelli, M. O. Myreen,
%  "x86-TSO: a rigorous and usable programmer's model for x86
%  multiprocessors", CACM 53(7):89-97, 2010 (x86 only lets a load pass
%  an earlier store sitting in the store buffer; the 386 had no fence
%  instruction, hence mb386 abusing IRET and mb586 abusing CPUID as
%  serializing instructions before SSE2's MFENCE).

### Kernel_x86.nw : <<function [[i8259init]](x86)>>
(line ~1129, section "IRQs (x86)" / commented "Interrupt controller [[i8259]]")
Algorithm/idea: programming the cascaded 8259A PIC pair (ICW1-ICW4,
  OCW3, master/slave on IRQ2, vector offset 32).
Verified: outb of ICW1..ICW4 to Int0ctl/Int0aux and Int1ctl/Int1aux,
  slave on level 2, VectorPIC offset, OCW3 to read ISR; i8259isr sends
  EOI.
CONFIDENCE: medium (datasheet title/edition from memory; no year given)
Proposed lines:
%ref: Intel, "8259A Programmable Interrupt Controller (8259A/8259A-2)"
%  datasheet (a chip designed for the 8080/8085, which is why ICW4 has
%  an "8086 mode" bit; two of them are cascaded, the slave on master
%  line 2, and i8259init moves their vectors to VectorPIC=32 so they
%  do not collide with the CPU's exception vectors 0-31).

### Kernel_x86.nw : <<global [[vectortable]](x86)>>
(line ~1341, section "Interrupt [[vectortable]] and [[idt]] (x86)")
Algorithm/idea: IDT, exception vs interrupt vectors, error-code-pushing
  exceptions.
Verified: each entry is CALL _strayintr/_strayintrx + BYTE vector; the
  x variant is for exceptions where the CPU pushes an error code;
  excname[] lists the 32 Intel-reserved exceptions; trap() is the single
  C entry point.
CONFIDENCE: high (bib key x86-refman exists; chapter number from
  memory, medium)
Proposed lines:
%ref: Intel, "Intel 80386 Programmer's Reference Manual", 1986,
%  chapter 9 "Exceptions and Interrupts" (the IDT and its gates, and
%  the table of which exceptions push an error code: the reason
%  vectortable calls _strayintrx for some vectors and _strayintr, which
%  pushes a dummy, for the others, so trap() always sees one Ureg
%  layout) [bib: x86-refman].

### Kernel_x86.nw : <<global [[gdt]](x86)>>
(line ~2088, section "Segmentation and [[gdt]] (x86)")
Algorithm/idea: hardware protection rings; segmentation as the road not
  taken.
Verified: all code/data descriptors are flat (base 0, limit 4GB,
  SEGG) and differ only by SEGPL(0) vs SEGPL(3); segmentation is used
  purely for kernel/user privilege, paging does the rest (author's own
  % note above the section says so).
CONFIDENCE: high
Proposed lines:
%ref: M. D. Schroeder, J. H. Saltzer, "A hardware architecture for
%  implementing protection rings", CACM 15(3):157-170, 1972 (Multics
%  ran its protection rings in software on the Honeywell 645; this
%  paper puts them in hardware; the 386 inherited four rings, and the
%  gdt uses only two, SEGPL(0) for the kernel and SEGPL(3) for users).
%ref: J. B. Dennis, "Segmentation and the design of multiprogrammed
%  computer systems", JACM 12(4):589-602, 1965 (the MIT view behind
%  Multics: one segment per procedure or data object, named and shared
%  by segment number; road not taken: every descriptor here is flat,
%  base 0 and limit 4GB, and paging does the real work).

### Kernel_x86.nw : <<function [[mmuwalk]](x86)>>
(line ~2190, section "Pagination and [[mmupd]], [[mmupt]] (x86)")
Algorithm/idea: two-level page-table walk (paging, invented on Atlas).
Verified: pd[PDX(va)] then table[PTX(va)], allocating a 2nd-level page
  on demand; PTESIZE entries are 4MB big pages.
CONFIDENCE: high
Proposed lines:
%ref: T. Kilburn, D. B. G. Edwards, M. J. Lanigan, F. H. Sumner,
%  "One-level storage system", IRE Trans. Electronic Computers
%  EC-11(2):223-235, 1962 (Manchester's Atlas made a small core memory
%  and a big drum look like one store, inventing pages and page
%  faults; Atlas kept one associative register per physical page,
%  where the 386 walks a two-level table in memory, pd[PDX(va)] then
%  pt[PTX(va)], exactly what mmuwalk does in software).
%ref: Intel 80386 Programmer's Reference Manual, 1986, section 5.2
%  "Page Translation" (the 10+10+12 bit split behind PDX and PTX, and
%  the PTE bits PTEVALID, PTEWRITE, PTEUSER) [bib: x86-refman].

### Kernel_x86.nw : <<function [[mmupdalloc]](x86)>>
(line ~2304, same section)
Algorithm/idea: per-CPU cache of pre-initialized objects (page
  directories already containing the kernel mappings copied from
  cpu->pdproto).
Verified: mmupdalloc pops cpu->mmupdpool if non-empty, else memmove's
  pdproto into a fresh page; mmupdfree pushes back up to 10.
CONFIDENCE: high (paper); the link is an analogy, noted as such
Proposed lines:
%ref: J. Bonwick, "The slab allocator: an object-caching kernel memory
%  allocator", USENIX Summer 1994 (for SunOS 5.4: keep freed kernel
%  objects already constructed so reuse skips initialization; the
%  small cpu->mmupdpool is the same trick, keeping page directories
%  that already hold the kernel mappings copied from cpu->pdproto).

### Kernel_x86.nw : <<function [[flushpg]](x86)>>
(line ~2471, same section)
Algorithm/idea: TLB invalidation; multiprocessor TLB consistency.
Verified: invlpg(va) on 486+, else reload CR3 (full flush). Only the
  local CPU is flushed; there is no cross-CPU shootdown IPI -- instead
  every context switch reloads CR3 (taskswitch/putcr3 in mmuswitch,
  mmuflushtlb in procsave), which flushes non-global entries.
CONFIDENCE: high
Proposed lines:
%ref: D. L. Black, R. F. Rashid, D. B. Golub, C. R. Hill, R. V. Baron,
%  "Translation lookaside buffer consistency: a software approach",
%  ASPLOS III, 1989 (from Mach on shared-memory multiprocessors, whose
%  TLBs were not kept coherent by hardware: a CPU changing a mapping
%  must interrupt the others to "shoot down" stale entries; flushpg
%  only invalidates the local TLB and the kernel relies instead on the
%  CR3 reload that each switch does in mmuswitch/procsave).

### Kernel_x86.nw : <<function [[gotolabel]](x86)>>
(line ~2621, section "Scheduling", subsection "[[arch_gotolabel()]] (x86)")
Algorithm/idea: context switch as setjmp/longjmp on a (sp, pc) label.
Verified: setlabel stores SP and return PC and returns 0; gotolabel
  restores them and returns 1 -- exactly V6 UNIX's savu/retu pair
  used by swtch().
CONFIDENCE: high (book); chapter not given
Proposed lines:
%ref: J. Lions, "A Commentary on the UNIX Operating System", 1977
%  (V6 UNIX on the PDP-11 switched processes with savu/retu, which save
%  and restore only the stack and frame pointers, the source of the
%  famous "You are not expected to understand this" comment in swtch;
%  setlabel/gotolabel are the same trick with an explicit Label of
%  (sp, pc), returning 0 on save and 1 on the jump back, like
%  setjmp/longjmp) [bib: lions].

### Kernel_x86.nw : <<function [[i8253init]](x86)>>
(line ~2797, section "Preemptive scheduling", subsection "Clock interrupt (x86)")
Algorithm/idea: periodic clock interrupt for time-slicing.
Verified: programs PIT counter 0 at Freq/Arch_HZ (100 Hz) in square
  wave mode; i8253clock -> timerintr() drives preemption.
CONFIDENCE: high
Proposed lines:
%ref: F. J. Corbato, M. Merwin-Daggett, R. C. Daley, "An experimental
%  time-sharing system", AFIPS Spring Joint Computer Conference, 1962
%  (CTSS at MIT: an IBM 7090 given an interval-timer clock so the
%  supervisor could take the CPU back from a user program that never
%  gives it up; i8253init sets the PC's timer chip to fire Arch_HZ=100
%  times per second for the same purpose, via timerintr()).

### Kernel_x86.nw : <<global [[_multibootheader]](x86)>>
(line ~2936, chapter "Initialization", subsection "Loading the kernel in physical memory (x86)")
Algorithm/idea: Multiboot boot protocol header.
Verified: magic 0x1BADB002, flags 0x00010003 (bit 16 = a.out kludge
  address fields), checksum = -(magic+flags), then header/load/
  load_end/bss_end/entry addresses -- the Multiboot 0.6 layout,
  needed because Plan 9's a.out is not ELF.
CONFIDENCE: medium (authors/version from memory)
Proposed lines:
%ref: B. Ford, E. S. Boleyn (and later Y. K. Okuji et al.), "Multiboot
%  Specification", version 0.6.96, Free Software Foundation (written so
%  any compliant loader such as GRUB can boot any OS kernel; loaders
%  expect ELF, and Plan 9's kernel is an a.out, so flag bit 16, the
%  "a.out kludge", tells GRUB to use the explicit load_addr,
%  load_end_addr, bss_end_addr and entry_addr fields of this header).

### Kernel_x86.nw : <<function [[mapfree]](x86)>>
(line ~3519, section "Kernel initialization (x86)", subsection "Memory detection (x86)")
Algorithm/idea: resource map allocator: sorted array of (addr,size)
  holes, first-fit allocation, coalescing free.
Verified: mapfree merges with the previous and/or next hole, else
  shifts the tail of the array to insert; mapalloc is first-fit (plus
  alignment and optional fixed address, returning the alignment slop to
  the map). This is V6 UNIX's malloc(map,size)/mfree (coremap/swapmap)
  almost verbatim, extended with alignment.
CONFIDENCE: high
Proposed lines:
%ref: J. Lions, "A Commentary on the UNIX Operating System", 1977 (V6
%  managed both core and swap space with malloc(map,size)/mfree over
%  sorted arrays of (size,addr) holes named coremap and swapmap; this
%  code is that pair almost verbatim, with alignment and a fixed-
%  address request added to mapalloc) [bib: lions].
%ref: D. E. Knuth, "The Art of Computer Programming", vol. 1, section
%  2.5 "Dynamic Storage Allocation" (first-fit, used by mapalloc, and
%  merging a freed area with its neighbors, the two-sided merge at the
%  top of mapfree) [bib: taocp].

### Kernel_x86.nw : <<function [[mathemu]](x86)>>
(line ~5961, section "Floating point (x86)", subsection "[[mathxxx()]]")
Algorithm/idea: lazy FPU context switching via the
  "coprocessor not available" trap (CR0.TS / fpoff).
Verified: procsave saves only if FPactive and leaves the FPU off;
  mathemu (VectorCNA handler) does fpinit on first use (FPinit) or
  fprestore (FPinactive) on demand.
CONFIDENCE: high (Intel chapter number medium)
Proposed lines:
%ref: Intel 80386 Programmer's Reference Manual, 1986, chapter 11
%  "Coprocessing and Multiprocessing" (the 387 was a separate chip, and
%  the CR0.TS "task switched" bit makes the next FP instruction trap
%  (exception 7, VectorCNA) so an OS can switch FP state lazily:
%  procsave leaves the FPU off, and mathemu restores or initializes it
%  only when the process really uses floating point) [bib: x86-refman].
%ref: J. Stecklina, T. Prescher, "LazyFP: Leaking FPU register state
%  using microarchitectural side-channels", arXiv:1806.07480, 2018
%  (speculative execution could read FP registers left in place for
%  the previous owner, the very state lazy switching leaves around;
%  after it, Linux and others switched to eager save/restore).

### Kernel_arm.nw : <<function [[setupcpop]](arm)>>
(line ~249, section "[[arch/arm/]]")
Algorithm/idea: generate an MRC/MCR instruction at runtime (the
  coprocessor fields are immediates in the encoding), then call it;
  requires D-cache writeback + I-cache invalidate.
Verified: builds opcode|op1<<21|crn<<16|cp<<8|op2<<5|crm followed by a
  MOV R14,R15 return, cachedwbse + cacheiinv, and cprd/cpwr call it
  through a function pointer.
CONFIDENCE: high for ARM ARM; medium for the relevance of the Blit
  paper (lineage/analogy only)
Proposed lines:
%ref: D. Seal (ed.), "ARM Architecture Reference Manual", 2001 (MRC/MCR
%  encode the coprocessor number and registers as immediate bits of
%  the instruction, so a generic cprd(cp,op1,crn,crm,op2) cannot be
%  written in assembly once; setupcpop assembles the word at run time,
%  and must clean the D-cache and invalidate the I-cache first so the
%  CPU fetches the new code, not stale bytes) [bib: arm-refman].
%ref: R. Pike, B. Locanthi, J. Reiser, "Hardware/software tradeoffs for
%  bitmap graphics on the Blit", Software-Practice and Experience
%  15(2):131-151, 1985 (on the Blit terminal's 68000, bitblt compiled
%  its inner loop on the fly; the same Bell Labs habit of generating
%  instructions at run time, here for a single coprocessor access).

### Kernel_arm.nw : <<function [[dmastart]](arm)>>
(line ~4354, section "[[buses/arm/]]")
Algorithm/idea: descriptor ("control block") driven DMA with software
  cache coherence for a non-coherent DMA engine.
Verified: fills a Cb (ti, sourcead, destad, txfrlen, stride,
  nextconbk), writes its bus address to Conblkad, sets Active;
  cachedwbse before memory->device, cachedinvse before device->memory.
CONFIDENCE: high (chapter number from memory, medium)
Proposed lines:
%ref: Broadcom, "BCM2835 ARM Peripherals", 2012, chapter 4 "DMA
%  Controller" (the engine does not read registers for a transfer but
%  a Cb "control block" in memory, which can chain via nextconbk; it
%  sees memory through the GPU's bus addresses, hence dmaaddr and
%  dmaioaddr, and it bypasses the ARM caches, hence the cachedwbse
%  before a memory->device copy and cachedinvse before device->memory).

### Kernel_arm.nw : <<function [[gpiosel]](arm)>>

### Kernel_arm.nw : <<function [[ctltrans]](arm)>>
(line ~3495, section "[[buses/arm/]]" (usbdwc.c))
Algorithm/idea: USB control transfer = SETUP stage, optional DATA
  stage, STATUS stage in the opposite direction, with DATA0/DATA1
  toggling.
Verified: chanio(..., SETUP, req, Rsetuplen), then data in/out with
  DATA1, then a zero-length DATA1 status transaction in the reverse
  direction; Rd2h bit of bmRequestType selects direction.
CONFIDENCE: high (spec); chapter numbers medium
Proposed lines:
%ref: Compaq, HP, Intel, Lucent, Microsoft, NEC, Philips, "Universal

### Machine.nw : <<function [[run]]>>
(line ~3263, section "[[run()]]")
Algorithm/idea: the stored-program fetch-decode-execute cycle.
Verified: do { ar = PC; instr = ifetch(ar); decode; if(cond) execute;
  PC += 4; } while(--count).
CONFIDENCE: high
Proposed lines:
%ref: J. von Neumann, "First Draft of a Report on the EDVAC", Moore
%  School, University of Pennsylvania, 1945 (ENIAC was programmed by
%  rewiring; for its successor EDVAC, with mercury delay-line memory,
%  von Neumann described keeping the orders in the same memory as the
%  numbers and having a central control fetch and obey them one after
%  another; run() is that control: ifetch, arm_class, (*ip->func)(),
%  then PC += 4).

### Machine.nw : <<global [[itab]]>>
(line ~2233, section "[[Inst]] and [[itab]]")
Algorithm/idea: interpreter dispatch through a table of handler
  function pointers.
Verified: run() does (*itab[arm_class(instr)].func)(instr): decode to
  an index, then an indirect call; no threading, no predecoding.
CONFIDENCE: high
Proposed lines:
%ref: J. R. Bell, "Threaded code", CACM 16(6):370-372, 1973 (from DEC's
%  PDP-11 FORTRAN: compile a program to a list of routine addresses,
%  each routine ending with a jump to the next, so there is no central
%  loop; road not taken: 5i goes back to run() after each
%  (*itab[op].func)() call).
%ref: M. A. Ertl, D. Gregg, "The structure and performance of efficient
%  interpreters", Journal of Instruction-Level Parallelism 5, 2003
%  (measures why a single shared dispatch point, like the indirect
%  call in run(), makes branch predictors miss, and why threaded code
%  predicts better).

### Machine.nw : <<function [[arm_class]]>>
(line ~3375, section "[[arm_class()]]")
Algorithm/idea: hand-written instruction decoder (bits 25-27 first,
  then refine); re-decoded on every execution.
Verified: switch on (w>>25)&7 then per-class bit tests, copied from
  libmach/5db.c; nothing caches the decode, so a loop body is decoded
  again each iteration.
CONFIDENCE: high for Ramsey-Fernandez; medium for Bedichek (venue/year
  confident, content summary from memory)
Proposed lines:
%ref: N. Ramsey, M. F. Fernandez, "Specifying representations of
%  machine instructions", ACM TOPLAS 19(3):492-524, 1997 (the New
%  Jersey Machine-Code Toolkit generates encoders and decoders for
%  MIPS, SPARC and x86 from a declarative description of bit fields;
%  road not taken: arm_class is a hand-written decoder copied from the
%  libmach/5db.c disassembler).
%ref: R. Bedichek, "Some efficient architecture simulation techniques",
%  USENIX Winter Conference, 1990 (a fast simulator decodes each
%  instruction once and caches the decoded form; road not taken: 5i
%  calls arm_class again every time a loop body runs).

### Machine.nw : <<[[run()]] switch [[reg.compare_op]] to set [[execute]]>>
(line ~5449, section "Control flow", subsection "ARM Conditional execution")
Algorithm/idea: lazy condition codes: store the operands and the kind
  of the last flag-setting operation, compute N/Z/C/V only when a
  condition is tested.
Verified: flag-setting ops store reg.cc1, reg.cc2, reg.compare_op
  (CCcmp/CCtst/CCteq); runcmp/runteq/runtst evaluate the 4-bit
  condition from them. Differs from QEMU in that no V flag is ever
  materialized (signed conditions are evaluated as C comparisons of
  cc1/cc2).
CONFIDENCE: high
Proposed lines:
%ref: F. Bellard, "QEMU, a fast and portable dynamic translator",
%  USENIX Annual Technical Conference (FREENIX track), 2005 (for x86
%  guests, whose flags are set by almost every instruction and rarely
%  read, QEMU records only the operands and the kind of the last
%  operation (CC_SRC, CC_DST, CC_OP) and derives the flags on demand;
%  5i's cc1, cc2 and compare_op are the same idea, evaluated by
%  runcmp/runteq/runtst, but they never compute an overflow V flag).

### Machine.nw : <<function [[isum]]>>
