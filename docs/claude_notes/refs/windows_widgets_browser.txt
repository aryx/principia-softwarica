### Windows.nw : <<function [[mousethread]]>>
(line ~3386, section "Mouse thread")
Algorithm/idea: handling the mouse with a process that loops reading
  mouse states, instead of with a state machine driven by events.
Verified: mousethread() is an endless alt() loop on mousectl->c; the
  modal helpers it calls (sweep, drag, menuhit) each run their own
  "while(mouse->buttons...) readmouse()" loop instead of keeping
  event-driven state.
CONFIDENCE: high
Proposed lines:
%ref: L. Cardelli and R. Pike, "Squeak: a Language for Communicating
%  with Mice", SIGGRAPH '85 (Computer Graphics 19(3):199-204), 1985
%  (for the Blit, a small language whose processes talked over
%  channels, used to write menus and scroll bars without
%  event-handling state machines; [[mousethread()]] and its
%  [[readmouse()]] loops are that idea, written in C with libthread).

### Windows.nw : <<function [[winctl]]>>
(line ~3904, section "Window threads: [[winctl()]]")
Algorithm/idea: one process per window, joined to the multiplexer by
  synchronous channels (keyboard, mouse, control).
Verified: every window runs its own winctl() thread, which alt()s over
  w->ck (runes), w->mc.c (Mouse), w->cctl (Wctlmesg), and later the
  cons/mouse read/write channels. This is the design of Pike's 1989
  paper, where each client gets a K (chan of int) and M (chan of Mouse)
  from the window system.
CONFIDENCE: high
Proposed lines:
%ref: R. Pike, "A Concurrent Window System", Computing Systems
%  2(2):133-153, 1989 [bib: concurrent-window-system] (the whole window
%  system in under 300 lines of Newsqueak: each window is a process fed
%  by a keyboard channel and a mouse channel, which is [[winctl()]]
%  with [[w->ck]] and [[w->mc.c]]; the paper also explains why this
%  beats the event-queue interface of X and NeWS).

### Windows.nw : <<[[winctl()]] alts adjustments>>  (the one at line ~14600)
(line ~14600, section "Application output events")
Algorithm/idea: guarded alternatives: disable an arm of alt() when its
  guard is false (here, flow control of application output).
Verified: before each alt(), alts[WCwrite].op is set to CHANNOP when
  !scrolling && !mouseopen && qh > org+nchars, so a writer on
  /dev/cons blocks until the user scrolls. That is a guarded input
  command; Plan 9 builds the guard by switching op to CHANNOP instead
  of writing "guard -> communication".
CONFIDENCE: high
Proposed lines:
%ref: E. W. Dijkstra, "Guarded commands, nondeterminacy and formal
%  derivation of programs", CACM 18(8):453-457, 1975 (where the
%  "guard -> action" alternative comes from; Hoare's CSP turned the
%  action into a communication, and libthread writes the guard by
%  hand, as the [[CHANNOP]]/[[CHANSND]] switch on [[alts[WCwrite].op]]).

### Windows.nw : <<function [[filsysproc]]>>
(line ~4258, section "Filesystem server proc")
Algorithm/idea: put each blocking system call in its own proc; keep all
  shared data in one proc whose threads switch only at channel
  operations, so they need no locks.
Verified: filsysproc() is created with proccreate() and blocks in
  read9pmsg(); it passes requests on channels to Xfid threads in the
  main proc. This is Pike's "Process vs. thread" slide word for word
  (1. blocking calls -> procs, 2. data shared by threads of one proc
  needs no locks).
CONFIDENCE: high
Proposed lines:
%ref: R. Pike, "Rio: Design of a Concurrent Window System", slides,
%  Bell Labs, 2000 [bib: rio-slides] (the "Process vs. thread" slide
%  gives the rule this chunk follows: a proc for every blocking call
%  such as [[read9pmsg()]], and all shared data in one proc whose
%  threads switch only at channel operations, so it needs no locks).

### Windows.nw : <<function [[xfidctl]]>>
(line ~4645, section "[[Xfid]] worker pool")
Algorithm/idea: pool of anonymous worker threads, each of which receives
  a function pointer over a channel and runs it.
Verified: the xfidctl() loop (f = recvp(x->c); (*f)(x); decref; sendp
  (cxfidfree, x)) and xfidallocthread()'s emalloc/chancreate/
  threadcreate(xfidctl, x, 16384) are the same code as on the "Xfids
  (2)" and "Xfids (3)" slides. (The prose right above already
  \cite{csp}s Hoare's book for the ownership argument; this ref is for
  the pool itself.)
CONFIDENCE: high
Proposed lines:
%ref: R. Pike, "Rio: Design of a Concurrent Window System", slides,
%  Bell Labs, 2000 [bib: rio-slides] (the "Xfids" slides show this
%  loop almost line for line: one Xfid carries one 9P message, and the
%  9P proc hands it over with [[sendp(x->c, xfidread)]], sending code
%  to run rather than data).
  (If the author prefers one rio-slides ref, keep this one and drop
  the [[filsysproc]] entry.)

### Windows.nw : <<struct [[Mousereadmesg]]>>
(line ~9937, section "[[/mnt/wsys/mouse]]")
Algorithm/idea: first-class channels: send a reply channel inside a
  message (channel of channels).
Verified: Mousereadmesg holds a Channel *cm (chan(Mouse)); xfidread
  receives it from w->mouseread and then does recv(mrm.cm, &ms). This
  is not possible in Hoare 1978 CSP, where you name processes, not
  channels.
CONFIDENCE: high
Proposed lines:
%ref: R. Pike, "The Implementation of Newsqueak", Software--Practice
%  and Experience 20(7):649-659, 1990 (Newsqueak made channels values
%  that can be sent over channels, which Hoare's 1978 CSP could not
%  do because it named processes; [[Mousereadmesg.cm]] is such a
%  channel, sent to get a fresh [[Mouse]] back).
%ref: R. Milner, J. Parrow and D. Walker, "A Calculus of Mobile
%  Processes, I and II", Information and Computation 100(1):1-77, 1992
%  (the pi-calculus: the theory of channels whose names travel over
%  channels; it came after Newsqueak).

### Windows.nw : <<function [[filsysmount]]>>
(line ~6211, section "Window creation")
Algorithm/idea: give each window its own /dev by mounting the window
  system's 9P service in the child's private name space.
Verified: mount(fs->cfd, -1, "/mnt/wsys", MREPL, "<id>") then
  bind("/mnt/wsys", "/dev", MBEFORE). The 8½ paper describes the same
  step as a single mount(cfd, "/dev", MBEFORE, buf); rio mounts at
  /mnt/wsys first and then unions it before /dev, and passes the window
  id as the mount spec (8½ passed a null string in the basic case).
CONFIDENCE: high
Proposed lines:
%ref: R. Pike, "8 1/2, the Plan 9 Window System", USENIX Summer Conf.,
%  1991, pp. 257-265 [bib: eight-and-a-half] (describes this step: the
%  child copies the parent's name space, then mounts the window
%  system's pipe before [[/dev]] so its [[cons]] and [[mouse]] hide
%  the real ones; [[rio]] mounts on [[/mnt/wsys]] first and then does
%  [[bind]] with [[MBEFORE]], passing the window id as the mount spec).

### Windows.nw : <<function [[sweep]]>>
(line ~6408, section "Window creation")
Algorithm/idea: rubber-banding: continuous feedback of a shape
  following the pointer while a button is held.
Verified: while(mouse->buttons == 4) readmouse(); r=canonrect(Rpt(p0,p));
  allocate a grey window image + red border at r, free the previous
  one. Unlike the classic XOR rubber band, rio redraws with a real
  layer (allocwindow) and lets the layer code restore what was
  underneath.
CONFIDENCE: high
Proposed lines:
%ref: I. E. Sutherland, "Sketchpad: A Man-Machine Graphical
%  Communication System", AFIPS Spring Joint Computer Conf. 23:329-346,
%  1963 (the first rubber-band lines, drawn with a light pen on the
%  TX-2 display; [[sweep()]] makes a rubber-band rectangle, not with
%  XOR drawing but by allocating a new layer at each mouse move; mux
%  on the Blit used the same button-3 gesture to make a window).

### Windows.nw : <<function [[winsert]]>>
(line ~13084, section "Content modification")
Algorithm/idea: text buffer as a flat array, shifting the tail on each
  insert (road not taken: buffer gap).
Verified: runemove(w->r+q0+n, w->r+q0, w->nr-q0) then copy; the
  surrounding prose already names the gap buffer and says rio skips
  it, but does not cite anything.
CONFIDENCE: medium (existence of the book is certain; the chapter
  title, "The Internal Sub-Editor", is from memory)
Proposed lines:
%ref: C. A. Finseth, "The Craft of Text Editing: Emacs for the Modern
%  World", Springer, 1991, chapter "The Internal Sub-Editor" (road not
%  taken: the buffer gap of Emacs-family editors keeps a hole at the
%  cursor so typing there moves nothing; [[winsert()]] instead
%  [[runemove()]]s the tail, which is free when you insert at the end,
%  as a terminal almost always does).

### Windows.nw : <<[[winsert()]] adjust cursors>>
(line ~13112, section "Content modification")
Algorithm/idea: the "output point": boundary between text the host has
  seen and text still being typed.
Verified: q0/q1 advance with <= but qh with <, so output inserted at qh
  goes before typed input; WCwrite inserts at qh and advances it. The
  transparent paper defines this exact concept for mux ("Mux has no
  current line; instead there is ... the output point"), including
  "prompt always appears at the output point". The paper also says mux
  kept only ~10,000 characters per window (rio's HiWater is 640000).
CONFIDENCE: high
Proposed lines:
%ref: R. Pike, "Window Systems Should Be Transparent", Computing Systems
%  1(3), 1988 [bib: window-system-should-be-transparent] (defines the
%  output point [[qh]] for mux, the Blit window system: host output is
%  inserted there, typed text after it, so a prompt never splits a
%  half-typed line; mux kept about 10,000 characters per window, rio's
%  [[HiWater]] keeps 640,000).

### Windows.nw : <<function [[wscroll]]>>
(line ~15047, section "Scroll bar interaction")
Algorithm/idea: Blit/mux three-button scroll bar where each button acts
  differently depending on the y position.
Verified: button 1 -> wbacknl(org, lines from y), button 2 ->
  p0 = nr*y/h absolute jump, button 3 -> frcharofpt at y becomes org;
  200ms first delay then wscrsleep repeat. Pike's paper says the mux
  scroll bar is "probably the least satisfactory part of the user
  interface" and that it should change the cursor to show what each
  button does. rio does not change the cursor either.
CONFIDENCE: high
Proposed lines:
%ref: R. Pike, "Window Systems Should Be Transparent", Computing Systems
%  1(3), 1988 (the author himself calls this three-button, position-
%  dependent scroll bar "probably the least satisfactory part" of mux
%  and "a topic for further research"; [[wscroll()]] keeps the design
%  and adds the 200ms delay before auto-repeat).

### Windows.nw : <<function [[timerproc]]>>
(line ~16611, section "Timer")
Algorithm/idea: timer facility; this one is the naive scheme (unsorted
  array, decrement every timer each tick).
Verified: every sleep(1), loop i<nt: x->dt -= dt; fire via nbsendul
  when <= 0, memmove to delete. O(n) per tick, which is Varghese-Lauck's
  "scheme 1"; fine here because rio has at most a few timers
  (scroll-repeat only).
CONFIDENCE: high
Proposed lines:
%ref: G. Varghese and T. Lauck, "Hashed and Hierarchical Timing Wheels:
%  Data Structures for the Efficient Implementation of a Timer
%  Facility", SOSP 1987 (road not taken: [[timerproc()]] is the
%  simplest scheme, an unsorted array that it walks every millisecond
%  to decrement each [[dt]]; timing wheels make each tick O(1), but
%  [[rio]] rarely has more than one timer, the scroll-repeat one).

### Windows.nw : <<function [[wdoubleclick]]>>
(line ~18734, section "Advanced terminal editing", subsection "Word
selection")
Algorithm/idea: double-click selection that matches brackets, quotes and
  lines ("programmer's double click").
Verified: left[]/right[] tables of brackets, newline, quotes;
  wclickmatch counts nesting; otherwise extends over alnum. The sam
  paper describes exactly this: double click in a word selects the
  word, just inside a bracket selects the bracketed text "handling
  nested brackets correctly", likewise parentheses and quotes.
CONFIDENCE: high
Proposed lines:
%ref: R. Pike, "The Text Editor sam", Software--Practice and Experience

%  these rules "reflect a bias toward programmers", since a word
%  processor would select sentences instead).

### Windows.nw : <<struct [[Frbox]]>>
(line ~21263, section "Boxes, strings, and coordinates")
Algorithm/idea: the frame as a list of boxes tiling the window, with
  special one-character boxes for newline and tab.
Verified: the sam paper's "Screen update" section: "A Frame contains a
  list of Boxes, each of which defines a horizontal strip of text";
  invariant: drawing str in the box reproduces its image; "Two special
  kinds of Boxes contain a single character: either a newline or a
  tab", newline box extends to the right edge, tab width depends on
  position with minimum width of a blank. Frbox differs: nrune<0 +
  bc/minwid instead of str; no stored Rectangle (positions recomputed
  with _fradvance); wid cached.
CONFIDENCE: high
Proposed lines:
%ref: R. Pike, "The Text Editor sam", Software--Practice and Experience
%  17(11):813-845, 1987, section "Screen update" (libframe was written
%  for sam's terminal program on the Blit; the paper's Boxes, strips
%  of text with newline and tab each in a box of their own, are
%  [[Frbox]], where [[nrune < 0]] marks a newline or tab and
%  [[minwid]] is the tab's minimum width).

### Windows.nw : <<function [[frdelete]]>>
(line ~22806, section "Incremental rendering")
Algorithm/idea: incremental deletion by copying tiles with bitblt over
  the "Z-shape" and switching to two block copies once columns align.
Verified: loop "while(pt1.x!=pt0.x && n1<f->nbox)" copies each box
  image from pt1 to pt0 with draw(); then, if lines changed, two draw()
  calls move the rest up, frselectpaint clears the bottom, _frclean
  merges adjacent boxes. Exactly the paper's algorithm ("tiles are
  copied ... until the old and new x coordinates are the same ... a
  sequence of at most two bitblts ... merge horizontally adjacent
  Boxes"). The paper also says frinsert makes four passes.
CONFIDENCE: high
Proposed lines:
%ref: R. Pike, "The Text Editor sam", Software--Practice and Experience
%  17(11):813-845, 1987 (the paper describes this function: remove the
%  "Z-shape" of deleted text, copy the following tiles back one by one
%  with bitblt until old and new x line up, move the rest with at most
%  two big copies, then merge neighboring boxes; here the copies are
%  [[draw()]] calls and the merge is [[_frclean()]]).

### Intro.nw : subsection "Input focus", paragraph "[[rio]] sits on the
click-to-focus side." (line ~1607)
Algorithm/idea: click-to-focus rationale.
Verified: the transparent paper says mux requires a click because it is
  sometimes useful to type into a mostly obscured window and to move the
  cursor out of the way without changing windows; wtop() raises the
  window and makes it current in one click.
CONFIDENCE: high
Proposed lines:
%ref: R. Pike, "Window Systems Should Be Transparent", Computing Systems
%  1(3), 1988 [bib: window-system-should-be-transparent] (gives mux's
%  reasons for click-to-focus: you may want to type into a mostly
%  hidden window, or move the pointer out of the way without changing
